# 데이터셋 검증기

스키마 정의서 v0.2 §10 의 배포 전 필수 검사를 구현합니다.
**이 검증을 통과하지 못한 데이터는 배포하지 않습니다.**

```
validator/
├── validate_dataset.py   검증기
├── make_fixture.py       합성 픽스처 생성기 (검증기 자체 시험용)
└── README.md
```

## 설치

```bash
pip install pandas pyarrow numpy pyyaml
```

Isaac Sim 이나 lerobot 은 필요 없습니다. 검증기는 파일만 읽으므로
개발 PC, 서버, CI 어디서든 동일하게 돌아갑니다.

## 사용

```bash
# 기본
python validate_dataset.py /path/to/keti-humanoid-hri-safety

# 리포트 저장
python validate_dataset.py <루트> --json reports/validation_v26.11.0.json

# WARN 도 실패로 처리. 조항 참조만 실린 임계값(정본에서는 `intrusion_distance` 1건)을 싣는 배포본에서는
# 그 항목이 WARN 이라 통과하지 않습니다(§9.3.1 — 26.11 배포본은 그 규칙을 싣지 않아 WARN 0). 새 WARN 은 개수로 비교하십시오
python validate_dataset.py <루트> --strict

# 생성 중 빠른 점검
python validate_dataset.py <루트> --checks C2,C8 --file-limit 5

# 시드 재현성까지 (Isaac Sim 필요)
python validate_dataset.py <루트> --repro-hook ./rerun_seed.sh --repro-sample 5
```

### 종료 코드
| 코드 | 의미 |
|---|---|
| 0 | 통과 |
| 1 | ERROR 존재 — 배포 불가 |
| 2 | `--strict` 에서 WARN 존재 |
| 3 | 검증기 실행 실패 — 없는 검사 ID(`--checks`) · 실행 중 예외 · 보고서를 쓰지 못함 |

인자의 꼴이 틀리면(`root` 가 빠짐 · 모르는 플래그 · 수가 아닌 `--repro-sample` 등) 인자 해석기(argparse)가 사용법을 찍고
**2** 로 멈춥니다 — 표의 3 이 아닙니다. `--strict` 의 2 와는 표준오류의 사용법 줄로 가릅니다.

**JSON 을 읽지 못하는 것은 3 이 아니라 ERROR 입니다.** 파이썬의 `json` 은 문법 오류 말고도 셋을 읽지 않습니다 —
UTF-8 이 아닌 바이트, 해석기의 자릿수 한도(기본 4300자리)를 넘는 정수, 디코더의 깊이를 넘는 중첩. 메타 파일이 그러면 C1 의
「JSON 파싱 실패」, 에피소드 표의 JSON 문자열 칸(`json_encoded_fields.episode`)이 그러면 C5 의 「… 가 JSON 으로 읽히지 않음」이고,
그 뒤의 보고는 문법 오류일 때와 같습니다. 스텝 표의 JSON 칸(`json_encoded_fields.step`)은 목록이어야 하므로, 목록으로 읽히지
않으면 — 문법 오류 · 자릿수 한도 · 깊이 때문이든, 객체 · 수 · 문자열이든 — ERROR 입니다(`region_names` 는 C3 의 「… 가 리스트
아님」, 나머지 둘은 C8 의 「… 가 JSON 배열로 읽히지 않음」. C8 은 빈 칸(null)을 말하지 않습니다 — C7 이 말합니다). 목록 안의
원소는 글자로 읽어 허용값과 대 봅니다 — 문자열이 아닌 원소는 허용되지 않은 값으로 나옵니다(관절 이름은 따로 「문자열 아닌
원소」로 — 매핑의 이름은 배포본이 정하므로 숫자 `1` 이 이름 `"1"` 로 읽히면 안 됩니다). 숫자형 열의 NaN 은 빈 칸이 아니라 값이라
C8 이 「… 가 JSON 배열로 읽히지 않음」으로 말합니다.

**읽히지만 기대한 꼴이 아닌 JSON 에서도 검증기는 멈추지 않고, 대개 ERROR 로 말합니다** — 목록 자리의 수 ·
객체 자리의 목록 · 문자열이 아닌 원소 · 재귀로 따라가지 못할 깊이 · `int()` 가 읽지 못하는 긴 숫자 문자열(팩의 키 · `episode_id` 의
번호와 시드). 잰 범위는 메타 파일 전체와 그 멤버, 그 아래 한 단계, 최상위 목록과 매핑의 첫 항목의 멤버, 에피소드 JSON 칸의 멤버에
몇 가지 꼴(`[[]]` · `[1, "x"]` · `5` · `"s"` · `{}` · `[]` · `null` 등)을 넣은 것입니다. 보고는 배포본이 담은 짝 없는 서로게이트(JSON
의 `"\ud800"`)도 터미널에는 이스케이프로, `--json` 보고서에는 받은 그대로의 JSON 이스케이프로 싣고, 보고서를 만들지 못하면
exit 3 입니다.
**보지 않는 것** — 읽힌 JSON 안의 수가 실수로 바꿀 수 없을 만큼 큰 정수(자릿수 한도 안)일 때 그 수를 쓰는 자리 · 관절 매핑
YAML 의 꼴(`unmapped` 가 문자열의 목록이 아니거나 `canonical_map` 이 객체가 아닌 것) · 위에서 잰 범위보다 깊은 자리의 꼴. 앞의 둘은
검증기를 멈출 수 있습니다(실측 — 앞의 것은 임계값 · `features` 의 `shape` · `notes` 의 수 · 카메라 정본의 `fps`, 뒤의 것은 멈추거나
말없이 지나갑니다). 꼴이 틀려도 ERROR 가 아닌 자리가 있습니다(실측 — 버전 · 설명 문장 같은 멤버, `sim_backend` 의 버전 칸).

### 에피소드가 가리키는 행 — C7

LeRobot v3.0 은 에피소드마다 파일을 두지 않습니다. 여러 에피소드가 한 parquet 을 나눠 쓰고, 어느 행이 어느
에피소드인지는 `meta/episodes` 의 포인터가 말합니다 — `dataset_from_index` · `dataset_to_index`(스텝 표에서의 자리
`[from, to)`) · `data/chunk_index` · `data/file_index`(그 행이 든 파일) · `length`. 적재기는 행의 `episode_index` 가
아니라 **이 포인터로** 읽습니다. 다른 검사는 모두 행을 `episode_index` 로 묶어 읽으므로, 포인터가 다른 에피소드의 행을
가리켜도 보지 못합니다 — 이 검사가 그 자리를 봅니다(영상 구간을 보는 카메라 배포본 C7 의 데이터 쪽 짝).

적재기가 읽는 대로 읽습니다(lerobot 0.6.1).

| 무엇을 | 어떻게 |
|---|---|
| 스텝 표 · 에피소드 표 | `data/<chunk>/<file>.parquet` · `meta/episodes/<chunk>/<file>.parquet` — 한 단계 아래의 파일만, 이름 순서로(글자 순서 — `file-10` 이 `file-2` 앞), 행은 저장된 순서로. 그 밖의 자리에 있는 parquet 은 표에 넣지 않습니다(넣어서 세면 적재기가 받지 못하는 표를 온전하다고 하게 됩니다) — 스텝 쪽은 그 파일을 빼고 대조하고, 에피소드 표 쪽은 대조하지 않습니다(검증기가 읽은 표가 더는 적재기의 표가 아니어서). 적재기가 읽는 자리에 에피소드 parquet 이 하나도 없을 때도 대조하지 않습니다. **그런 파일이 있다 · 표가 없다는 말은 아래 「적재기가 표를 여는가」가 합니다** — 읽은 스텝이 하나도 없어 이 대조가 돌지 않을 때도 말하도록 |
| 에피소드 k 의 포인터 | 에피소드 표의 **k번째 행** — 그 행의 `episode_index` 가 k 가 아니면 ERROR |
| 구간 | `0 ≤ from < to ≤ 스텝 표의 행 수` · `to − from = length` · 그 행들의 `episode_index` 가 모두 k · `frame_index` 가 0, 1, 2, … · 스텝 표의 `index` 가 행의 자리와 같음(`index` 로 골라 읽는 쪽도 같은 행을 얻습니다) |
| 파일 | `info.json` 의 `data_path`(없으면 v3.0 의 틀)를 `data/chunk_index` · `data/file_index` 로 푼 파일에 그 구간의 행이 모두 있음 — 에피소드를 골라 받으면 LeRobot 은 그 파일만 받습니다. 틀이 어떤 에피소드의 번호로 풀리지 않으면 그 에피소드의 ERROR 입니다(틀 자체가 못 쓰는 것이면 `meta/info.json` 에 한 번). 파일 시스템이 받지 않는 이름(너무 긴 경로)은 「없는 파일」입니다 |
| 남는 행 | 어느 에피소드도 가리키지 않는 스텝 행이 없음 |

포인터 다섯 열과 스텝 표의 `index` · `episode_index` · `frame_index` 는 **정수 열**이어야 합니다(배포본이 그렇게 싣습니다.
빈 칸이 있어 실수로 읽히는 열 · 문자열 · 참거짓은 자리가 아닙니다). 결함의 종류마다 문장이 하나이고 수는 위치에
적습니다 — 앞쪽에서 한 행이 빠지면 뒤의 에피소드가 모두 어긋나는데, 그것이 한 줄로 접혀 다른 오류를 가리지 않습니다.
보고서 JSON 의 `stats.data_spans` 가 대조한 에피소드 수와 행 수입니다(실측 2026-10-08 — S1d 400건 381,902행 ·
S1a 400건 383,462행 · S1d 시험 배치 20건 19,094행 모두 전부 대조 · ERROR 0, C7 만 돌려 1~2초).

**보지 않는 것** — 그 행에 든 값이 그 스텝의 값인지(포인터는 누구의 행인지만 말합니다 — 값은 C8 · C9) ·
`--file-limit` 로 읽지 않은 파일에 구간이 있는 에피소드(몇 개인지 INFO 로 말합니다) · 배포본이 놓인 경로의
글자(`datasets` 가 경로를 패턴으로 푸는 경우 — 라벨 재유도 도구가 봅니다). `info.json` 이 표를 옳게 세었는지는 아래
「info.json 이 세는 수」가 봅니다.

**같은 진술의 구현이 하나 더 있습니다** — 라벨 재유도 도구(`generation/labeling/check_release_labels.py` 의
`read_episodes` · `read_steps` · `check_spans`). 검증기는 `generation/` 을 import 하지 않아 따로 구현했고, 둘이 갈라지면
한쪽만 통과하는 배포본이 생깁니다. `tests/generation/test_pointer_readings_agree.py` 가 같은 결함을 둘에 넣어, 도구가
거부하는 것을 검증기도 말하는지 봅니다. **lerobot 판을 올려 적재기가 읽는 방식이 달라지면 둘을 함께** 고칩니다.

### 적재기가 표를 여는가 — C7

포인터가 옳은지보다 앞에 있는 물음입니다 — 적재기가 표를 받기는 하는가, 어느 파일에서. 아래는 적재기를 멈추는데
**pandas 로 읽으면 보이지 않아**, 위의 포인터 대조는 「전부 대조 · ERROR 0」 이라고 말합니다(2026-10-08 실제 적재기로
확인). 행은 읽지 않고 parquet 의 footer 와 `info.json` 만 봅니다 — 그래서 `--file-limit` 과
무관하게, 읽은 스텝이 있든 없든 적재기가 읽는 파일 전부를 봅니다.

| 무엇을 | 왜 |
|---|---|
| 표의 파일이 **적재기가 읽는 자리**에 있음 — `data/<chunk>/<file>.parquet` · `meta/episodes/<chunk>/<file>.parquet` | 그 밖의 자리의 parquet 은 적재기가 읽지 않습니다. 그 자리에 파일이 하나도 없으면 표가 없는 것이고 적재기는 열지 못합니다 — 검증기의 판독기는 어느 깊이든 읽고, 에피소드 표는 `meta/episodes.json(l)` 로 대신 읽기도 해서 따로 봐야 합니다. **청크 디렉터리가 심링크여도 그 안의 파일은 표의 파일입니다** — 적재기의 `glob("*/*.parquet")` 은 그 안으로 들어가고(실측), 검증기도 그 파일을 읽고 셉니다 |
| 표의 파일 경로(배포본 안에서의 경로)에 **`*` · `?` · `[` 가 없음** | LeRobot 은 표의 파일 경로를 `datasets` 에 넘기고, `datasets` 는 이 글자가 든 경로를 이름으로 열지 않고 패턴으로 풉니다. 실측 — `file-[1]00.parquet` 은 건너뜁니다(`[1]` 은 글자 `1` 에 맞습니다) · `file-00?.parquet` 과 `file-*.parquet` 은 이웃 `file-000.parquet` 을 한 번 더 읽습니다 · `chunk-00[0]` 아래에서는 아무것도 찾지 못합니다. 파일은 제자리에 온전하므로 행 수도 포인터도 「전부 대조」 로 지나갑니다. **패턴이 우연히 그 파일 하나에만 맞는 경우에도 말합니다**(닫히지 않은 `[` · 맞는 이웃이 없는 `?`) — 무엇을 읽는지가 디렉터리의 다른 파일에 달려 있기 때문입니다. 그 밖에 잰 글자 스물여섯 가지(`]` `{` `}` `!` `#` 공백 등)는 이름 그대로 읽힙니다 |
| 파일의 **첫 행 그룹이 0행**이 아님 | 빈 표를 parquet 으로 저장하면 0행짜리 행 그룹 하나가 됩니다. LeRobot 이 쓰는 `datasets` 는 파일의 첫 행 그룹의 행 수를 배치 크기로 쓰고 0 에서 실패합니다(실측 — 뒤에 행이 있어도 실패하고, 행 뒤의 빈 그룹이나 행 그룹이 아예 없는 파일은 읽힙니다). 이어 붙여 읽으면 그 파일은 그냥 사라집니다 |
| 한 파일에 **같은 이름의 열이 둘** 없음 | 판독기가 열을 이름으로 찾다 실패합니다 |
| **에피소드 표**의 파일들을 적재기가 한 표로 맞출 수 있음 — ① 포인터 열(`episode_index` · `length` · `dataset_from_index` · `dataset_to_index` · `data/chunk_index` · `data/file_index`)은 파일마다 같은 형 ② 뒤 파일의 열을 첫 파일의 형에 **값이 무엇이든 맞출 수 없는** 차이가 없음 ③ 첫 파일에 없는 열이 뒤 파일에 없음 | 적재기는 에피소드 표의 형을 **첫 파일**로 정하고 나머지를 거기에 맞춥니다. ②는 적재기의 캐스트(`datasets` 의 `cast_array_to_feature`)를 형만으로 옮긴 것입니다 — struct 는 첫 파일의 struct 에 제 필드가 모두 있어야 하고 필드마다 다시 · 목록은 목록에 원소의 형으로(고정 길이끼리는 길이도 같아야) · 빈 형(`null`)은 어디에나 들어감 · 값이 있는 잎 형은 목록 · struct · 빈 형에 못 들어감. 흔한 꼴은 **첫 파일의 값이 전부 비어 빈 형으로 실린 열**입니다(빈 목록뿐인 파일을 pandas 로 따로 저장하면 `list<null>`) — 그 반대 순서는 읽힙니다. ①은 들어가지 않는 값에서 실패하고 pandas 는 넓은 쪽으로 합쳐 `int8` 옆의 `int16` 을 정수 열 하나로 보여 줍니다 — LeRobot 이 늘 한 가지 형으로 쓰는 열이라 다르면 말합니다. **행 그룹이 없는 뒤 파일**은 판독기가 배치를 만들지 않아 맞추지도 않으므로 ①~③을 묻지 않습니다(첫 파일은 행 그룹이 없어도 표의 형을 정합니다) |
| `info.json` 의 `features` 가 `index` · `episode_index` · `frame_index` · `task_index` 를 선언했으면 **정수 하나** — `dtype` 이 `int8`~`uint64`, `shape` 이 `[1]` | 적재기는 스텝 표를 선언한 대로 바꿔 읽고, 읽은 `episode_index` 로 에피소드 표의 행을, `task_index` 로 과제 표의 행을 찾습니다 — parquet 이 `int64` 여도 `float32` 로 선언돼 있으면 `0.0` 으로 찾다 실패합니다. `shape` 이 `[1]` 이 아니면 수열로 읽으려다, `shape` 이 없거나 `dtype` 이 pyarrow 의 이름이 아니면(`long` · `<i8` 같은 numpy 의 이름) 표를 만들다 실패합니다(셋 다 실제 적재기로 확인 — `task_index` 는 실수 · 참거짓 · 문자열 · 모양 `[2]` · 모양 없음 · `long` 을 따로 쟀습니다) |

**②의 규칙은 적재기를 재서 맞춥니다.** 형 스무 가지의 순서쌍 400개를 적재기의 캐스트와 판독기에 넣어, 값을 어떻게
골라도 실패하는 쌍을 `tests/validator/loader_casts_measured.json` 에 적어 두었습니다(실측 2026-10-08 — lerobot 0.6.1 ·
datasets 4.8.5 · pyarrow 25.0.1 · 289쌍 실패, 두 방법의 답 일치). 규칙은 그 400쌍에서 **적재기가 읽는 것을 하나도
거부하지 않고**, 놓치는 것은 잎 형끼리 Arrow 에 변환이 아예 없는 12쌍뿐입니다(`binary` → `int64`, `timestamp` → `bool`
같은). `datasets` 판이 바뀌면 다시 잽니다(같은 명령이 아래 「features 가 선언한 스텝 표」의 측정도 함께 잽니다 — 둘 합쳐 약 15초).
LeRobot 이 든 인터프리터 `.venv-lerobot` 은 `generation/README.md` 「환경이 둘로 나뉘어 있습니다」대로 만듭니다 —

```bash
.venv-lerobot/bin/python scripts/measure_loader_casts.py            # 적어 둔 것과 대조 (다르면 exit 1)
.venv-lerobot/bin/python scripts/measure_loader_casts.py --write    # 다시 씀
```

보고서 JSON 의 `stats.table_files` 가 표마다 본 파일 수입니다. **보지 않는 것** — 배포본이 놓인 경로의 글자(배포본의 것이
아닙니다 — 받는 쪽이 `*` · `?` · `[` 가 든 디렉터리에 두면 같은 일이 납니다) · 에피소드 표의 파일 사이에서 적재기가
읽어 주거나 값에 따라 갈리는 차이(포인터 밖 열의 정수 폭 · 정수 옆의 실수 · 문자열 종류 · 뒤 파일의 빈 형이나 없는
열)와 위의 잎 형 12쌍 · 적재기가 형 자체를 받지 못하는 열(`map` 등 — 파일 사이의 차이가 아닙니다) · **스텝 표의 파일끼리의 형**(적재기는 스텝 표의 형을 첫 파일이 아니라 `features` 로 정합니다 — 파일마다 `features` 에 대 보는 것은 아래 「features 가 선언한 스텝 표」) ·
적재기가 읽지 않는 자리의 파일의 형과 행 그룹 · parquet 이 아닌 파일(읽다 실패한 것은 C1 이 말합니다).

### features 가 선언한 스텝 표 — C7

LeRobot 의 적재기는 스텝 표의 형을 파일에서 읽지 않습니다. `info.json` 의 `features` 로 표의 열과 형을 정하고 스텝
파일을 거기에 맞춰 넣습니다. 그래서 파일과 선언이 서로 다른 말을 하는 배포본은 적재기가 열지 못하거나, 값이 하나도 없는
열을 달고 열립니다 — 그런데 다른 검사는 모두 스텝을 pandas 로 읽으므로 파일은 온전해 보입니다. 이 검사가 둘을
**적재기가 맞추는 대로** 맞춰 봅니다.

적재기가 하는 일입니다(실측 2026-10-10 — lerobot 0.6.1 · datasets 4.8.5 · pyarrow 25.0.1, 사례 216가지. **카메라 영상이
있는 배포본과 없는 배포본에서 따로 쟀습니다.** 열리는가 멈추는가가 갈린 것은 하나이고, 두 배포본에 든 값이 달라서였습니다 —
상자 열을 `uint16` 으로 선언하면 보이지 않는 프레임의 `-1` 이 든 쪽만 멈춥니다. 표의 null 인 목록의 줄은 따로 쟀습니다 —
영상 없는 쪽에서 13가지, 있는 쪽에서 4가지이고 두 쪽의 결과가 같았습니다).

| 어긋난 것 | 적재기 |
|---|---|
| `info.json` 에 `features` 가 없음 · 객체가 아님 (`null` · 목록 · 문자열 · 수) | 여는 단계에서 멈춥니다. 빈 객체 `{}` 는 읽히고, 그러면 스텝 파일의 모든 열이 선언에 없는 열입니다(아래 줄) |
| 선언 하나를 열로 만들지 못함 — feature 가 객체가 아님 · `dtype` 이나 `shape` 이 없음 · `dtype` 이 pyarrow 의 형 이름이 아님(`<f8` · `long` · `int` · `str` · `boolean` · `object` 같은 다른 라이브러리의 이름, 대소문자나 공백이 다른 이름) · `shape` 이 길이를 잴 수 없는 것(`null` · 수 · 참거짓)이거나 비었거나 원소가 여섯 이상 · 원소 하나짜리 `shape` 의 그 길이가 `0` 이거나 문자열 · `null` | 여는 단계에서 멈춥니다 — 그 열이 파일에 있든 없든 |
| 스텝 파일에 **선언에 없는 열** | 여는 단계에서 멈춥니다. 영상(`dtype` 이 `video`)으로 선언한 이름은 스텝 표의 열이 아니어서, 그 이름의 열이 파일에 있어도 같습니다. 자리 열 넷(`index` · `episode_index` · `frame_index` · `task_index`)도 선언이 없으면 같습니다 |
| **선언은 있는데 파일에 없는 열** | **멈추지 않습니다** — 빈 값(null)으로 채워 열고, 그 파일의 스텝은 그 열에 `None` 을 달고 나옵니다(스텝 파일 둘 가운데 하나에만 없으면 그 파일의 스텝만. 두 차원 이상으로 선언한 열은 `None` 이 아니라 NaN 으로 찬 배열로 나옵니다). 자리 열은 따로입니다 — `index` 가 없으면 항목을 읽다 실패하고, `episode_index` 가 없으면 받은 사본이 모자란다고 보고 Hub 로 갑니다. 적재기가 열로 만들지 못하는 선언(위 줄)은 채우기 전에 멈추므로 이 줄이 아닙니다 |
| 저장된 형이 선언과 다르고 **바뀌지 않음** | 적재기는 저장된 열을 선언한 형으로 바꿉니다(`datasets` 의 `cast_array_to_feature`). 바뀌지 않으면 여는 단계에서 멈춥니다 — 값 하나로 선언한 열에 목록이나 struct(길이 1 의 목록도) · 목록으로 선언한 열에 값 하나 · 다른 길이로 고정된 목록 · 길이가 다른 목록이 하나라도 든 가변 길이 목록 · 선언한 형에 들어가지 않는 값(`int8` 옆의 `128`, 정수 옆의 `2.5` · `NaN`, 수 옆의 `"abc"`, 실수에 정확히 담기지 않는 큰 정수) |
| 가변 길이 목록으로 실린 열에 **null 인 목록**이 있고, 같은 행 그룹에서 그 뒤에 null 없는 배치가 옴 | 적재기는 파일을 배치로 나눠 바꿉니다 — 배치는 그 파일의 첫 행 그룹의 행 수만큼이고 행 그룹을 넘지 않습니다. null 이 든 배치는 바르게 바꾸지만, null 이 없는 배치는 「행의 자리 × 길이」에서 원소를 집습니다. null 인 목록은 원소가 없으므로 그 뒤의 배치는 목록 하나씩 밀린 자리를 읽습니다 — **오류 없이 다른 스텝의 목록을 내주거나**, 밀리다 행 그룹의 원소를 넘으면 여는 단계에서 멈춥니다. 다른 스텝의 목록이 제 것과 같은 값이면 나오는 값은 저장된 그대로입니다(모든 목록의 값이 같은 열은 밀려 읽혀도 저장된 대로 나옵니다). 뒤에 그런 배치가 없으면(행 그룹이 배치 하나이거나, 뒤의 배치마다 null 이 있으면) 바르게 읽힙니다. **배포본을 통째로 열 때의 일입니다** — 에피소드를 골라 열면 바르게 읽습니다(아래) |
| 저장된 형이 선언과 다르고 **바뀜** | 말없이 바꿔 읽습니다. 값이 그대로인 것도 있고(`int32` 에 들어가는 `int64` · 길이가 모두 선언과 같은 가변 길이 목록 · `large_string`) **달라지는 것도 있습니다** — `float64` 를 `float32` · `float16` 으로(`1e300` 은 `inf`), 수를 `bool` 로(`0.4` 는 `true`), 수를 `string` 으로 |

**검사가 말하는 것은 마지막 줄을 뺀 여섯 줄입니다 — 적재기를 멈추는 것 넷, 멈추지 않지만 값이 없는 열, 그리고 null 인
목록 뒤에서 잘못 읽히는 스텝.** 마지막 줄(말없이 달라지는 값)은 말하지 않습니다. LeRobot 의 기록기는 모든 열을 선언한 형
그대로 싣습니다(실측 — S1d 400건 · S1a 400건 · S1d 시험 배치 20건 모두 저장된 형이 선언한 형). 선언과 다른 형은 스텝 파일을
다른 도구로 다시 쓴 배포본에서 생깁니다 — pandas 를 거치면 고정 길이 목록이 가변 길이 목록이 됩니다(길이가 모두 선언과
같으면 읽힙니다. 픽스처의 스텝 파일이 그 꼴입니다). Arrow 의 확장 형으로 실린 열(고정 모양 텐서)은 그것이 싣는 형으로
봅니다 — 적재기가 그렇게 바꿉니다. 확장 형이 그 아래에 든 열(목록의 원소가 확장 형인 열)은 판단하지 않습니다(아래 「보지
않는 것」).

**위 표는 배포본을 통째로 열 때입니다**(`LeRobotDataset(repo_id, root=…)` — 기본). 에피소드를 골라 열면(`episodes=[…]`)
적재기는 행을 걸러 낸 뒤에 바꿉니다(실측 2026-10-10 — 다섯 스텝짜리 에피소드 둘, 하나씩 · 둘 다 골라서).

- 선언이나 열의 형 때문에 멈추는 것 — 선언에 없는 열 · 열로 만들지 못하는 선언 · 길이가 다르게 고정된 목록 · 값 하나로 선언한
  목록 — 은 어느 에피소드를 고르든 똑같이 멈추고, 파일에 없는 열도 똑같이 빕니다
- **값 하나나 목록 하나가 선언한 형에 들어가지 않아 멈추는 것**(`int8` 옆의 `300` · 길이가 다른 목록 하나)은 그 스텝이 든
  에피소드를 골랐을 때만 멈춥니다. 다른 에피소드만 고르면 열립니다
- **null 인 목록 뒤의 스텝은 잘못 읽히지 않습니다** — 에피소드를 전부 골라도 그렇습니다. 걸러 낸 배치는 제 행만 가진 배열이라
  밀릴 자리가 없습니다

검사가 말하는 것은 통째로 여는 쪽입니다. 스트리밍으로 읽는 쪽(`StreamingLeRobotDataset`)은 재지 않았습니다.

**null 인 목록의 줄은 null 이 있다는 말이 아닙니다.** 스텝 데이터의 null 은 그것만으로 결함이고 「스텝 데이터에 null 없음」이
말합니다 — 다만 그 검사는 `--file-limit` 이 읽게 둔 파일만 봅니다. 여기서 말하는 것은 그 null 때문에 **다른 스텝이 잘못
읽히는가**이고, 파일 전체로 보면 길이도 원소도 멀쩡해 행 그룹과 배치의 자리를 따져야 보입니다. 위치에는 밀린 자리에서
읽기 시작하는 행과 결과를 적습니다 — 멈추는 경우는 그대로, 멈추지 않는 경우는 **나오는 값이 실제로 달라질 때만** 말하고
값이 처음 달라지는 행을 함께 적습니다(밀려 읽은 목록이 제 것과 같은 값이면 스텝은 저장된 대로 나옵니다 — 그때는 말하지
않습니다).

자리 열 넷의 **선언한 폭**도 이 규칙입니다 — `int8` 로 선언한 `frame_index` 에 `128` 이 있으면 여는 단계에서 멈추고, 네 열
모두 같습니다(실측). 네 열이 정수 하나로 선언됐는지는 위 「적재기가 표를 여는가」가, 그 정수에 값이 들어가는지는 여기서
봅니다.

읽는 것은 `info.json` 과 적재기가 읽는 스텝 파일 전부의 스키마입니다 — `--file-limit` 과 무관하게 전부입니다. 행은
**저장된 형이 선언과 다른 열이 있는 파일에서만** 읽고, 적재기가 하는 바로 그 변환(Arrow 의 캐스트)을 해 봅니다. 행이 하나도
없는 스텝 파일은 건너뜁니다(실측 — 행 그룹이 없는 파일은 적재기가 맞추지도 않아, 선언에 없는 열이 있어도 나머지를 모두
읽습니다. 빈 행 그룹이 든 파일에서는 열을 보기 전에 멈춥니다 — 위 「적재기가 표를 여는가」의 줄입니다). 행이 읽히지 않는
파일은 SKIP 으로 남기고 본 수에서 뺍니다. `info.json` 이 없거나 JSON 객체로 읽히지 않으면 볼 것이 없고, 그것도 SKIP 으로
말합니다 — 그 파일의 결함은 C1 이 말하지만 `--checks C7` 만 돌리면 C1 은 돌지 않습니다. 결함의 종류마다 문장이 하나이고 수는 위치에 적습니다 — `features` 가
통째로 비면 모든 파일의 모든 열이 선언에 없는 열인데, 그것이 한 줄(첫 파일 · 그 파일의 열 넷까지 · 열의 수 · 파일의 수)로
접힙니다. 보고서 JSON 의 `stats.step_features` 가 본 파일 수(`files`) · 선언에 대 본 열의 수(`columns` — 파일마다 셉니다) ·
그 가운데 저장된 형이 달라 값을 읽어 바꿔 본 열의 수(`cast`)입니다(실측 2026-10-10 — S1d 400건 파일 4개 · 열 120 · 0,
S1a 400건 3 · 69 · 0, S1d 시험 배치 20건 1 · 30 · 0. 모두 ERROR 0).

**세 규칙은 적재기를 재서 맞춥니다** — 선언을 적재기가 무엇으로 만드는가(`_feature_column`) · 저장된 열이 선언한 형으로
바뀌는가(`_cast_stops`) · null 인 목록 뒤의 배치를 어디서 읽는가(`_null_lists_misread`).
`scripts/measure_loader_casts.py` 가 `tests/validator/feature_casts.py` 의 사례를 적재기 자신의
함수(`DatasetInfo` · `get_hf_features_from_features` · `load_nested_dataset`)에 넣어 잰 답을
`tests/validator/feature_casts_measured.json` 에 적어 두고, 시험이 규칙을 그 답과 사례마다 대조합니다(실측 2026-10-10 —
lerobot 0.6.1 · datasets 4.8.5 · pyarrow 25.0.1 · 파일을 읽는 사례는 메모리에서의 캐스트와 실제 판독기 두 방법으로 재고
두 답이 일치. `info.json` 의 `features` 가 통째로 없는 꼴 여섯은 읽을 파일이 없어 한 방법입니다).

- 선언의 꼴 110가지 가운데 적재기가 멈춘 것은 61가지이고, 검사는 그중 50가지를 말하고 11가지를 놓칩니다. 놓치는 것은
  검사가 **판단하지 않는 꼴**뿐입니다 — pyarrow 에 그 이름의 함수는 있는데 인자 없이는 형이 되지 않는 이름(`list` ·
  `struct` · `decimal128` · `timestamp` · `array`), 형을 만드는 함수가 아닌 이름, `shape` 의 길이가 음수 · 참거짓 · 소수 ·
  목록인 것. 적재기가 표를 만든 선언을 멈춘다고 하는 일은 없습니다
- 저장된 열 70가지 × 선언 22가지 = 1540쌍 가운데 적재기가 멈춘 것은 1126쌍이고, 규칙은 1540쌍 모두에서 적재기와
  같은 답을 냅니다
- null 인 목록의 자리 25가지(행 그룹의 나뉨과 null 의 자리) 가운데 적재기가 멈춘 것은 9가지, 열려서 다른 스텝의 값을
  내준 것은 2가지이고, 규칙은 25가지 모두에서 같은 답을 냅니다 — 값을 잘못 내준 사례에서는 처음 틀린 스텝까지 같습니다
  (멈춘 사례의 「밀린 자리에서 읽기 시작하는 행」은 메모리 쪽에서 본 것과 댑니다 — 멈춘 판독기는 아무것도 내주지 않습니다).
  모든 목록의 값이 같은 열로 같은 25가지를 다시 재면 멈추는 9가지는 그대로 멈추고 나머지는 전부 저장된 대로 읽힙니다.
  같은 25가지를 에피소드를 골라 읽으면 모두 저장된 대로 읽힙니다(에피소드 하나씩 · 둘 다 — 두 방법으로)

값의 변환은 **검증기를 돌리는 쪽의 pyarrow** 가 합니다(적재기가 부르는 그 함수를 부릅니다). 받는 쪽의 pyarrow 는 알 수
없습니다 — 정수 · 실수 · 참거짓 · 문자열과 그 목록 사이의 변환은 판마다 같고, 그 밖의 드문 형(`timestamp` · `decimal` ·
`binary` 등)은 잰 판과 다른 pyarrow 에서 답이 다를 수 있습니다. 시험도 그 쌍들은 잰 판과 같은 pyarrow 에서만 대조합니다.

**적재기가 열어 항목을 내주는데도 ERROR 인 것이 둘입니다** — 선언은 있는데 파일에 없는 열(그 열은 값이 없습니다)과, null 인
목록 뒤에서 다른 스텝의 값을 내주는 열(열리지만 값이 틀립니다).

**보지 않는 것** — 변환이 되면서 값이 달라지는 차이(위 표의 마지막 줄 — 적재기는 바꾼 값을 말없이 내줍니다) ·
판단하지 않는 선언의 형(두 차원 이상의 `shape` · `dtype` 이 `image` 인 열 · `timestamp[s]` 처럼 인자를 적은 `dtype` ·
길이가 `-1` · `true` · `3.0` 인 `shape` — 적재기는 이것들을 저마다 다르게 읽습니다). 이 열들도 스텝 표의 열이므로 파일에
없으면 말하고, 형은 대 보지 않습니다 · LeRobot 이 선언과 무관하게 제 형으로 읽는 두 열 `language_persistent` ·
`language_events`(선언돼 있으면 파일에 있어도 되는 열일 뿐, 그 밖에는 아무것도 말하지 않습니다) · **Arrow 의 확장 형이
그 아래에 든 열** — 목록의 원소나 struct 의 필드가 확장 형인 열은 스텝 표의 열로만 보고 형은 대 보지 않습니다(실측: 원소가
`json` 확장 형인 목록은 null 인 목록이 없으면 읽히고 하나라도 있으면 여는 단계에서 멈춥니다 — 그것이 전부인지는 재지
않았습니다) · **열리고 나서 항목을
만들지 못하는 선언** — 문자열의 목록(`string` 에 길이 3)이나 `binary` 로 선언한 열은 적재기가 표를 만들어 열고, 항목을
읽을 때마다 실패합니다(실측 — 텐서로 바꾸지 못합니다). 이 검사가 보는 것은 표가 만들어지는지까지입니다 · 스텝 파일끼리의 형(파일마다 `features` 에 맞출 수 있으면 읽힙니다) · 열 안의 빈 값 그 자체(위의 「스텝
데이터에 null 없음」이 봅니다 — 실측: 값이나 목록이 통째로 null 인 스텝은 그 열에 `None` 을 달고 나오고, 목록 안에 null 이
든 스텝은 그 항목에서 실패합니다. 적재기를 멈추는 것은 위 표의 null 인 목록 뒤의 배치뿐이었습니다) · `names` 와
그 밖의 키(적재기가 표를 만들 때 읽지 않습니다) · 영상 feature 의 `shape` 과 `info`(C1 의 카메라 검사) · 스텝 파일이
하나도 없는 배포본의 선언(위 「적재기가 표를 여는가」가 표가 없다고 말합니다).

### info.json 이 세는 수 — C7

LeRobot 은 표를 세지 않습니다. 에피소드 수와 스텝 수를 `meta/info.json` 의 `total_episodes` · `total_frames` 에서
읽고, `len(dataset)` 이 곧 `total_frames` 입니다. 표를 다시 쓴 뒤 이 수가 옛 값으로 남아도 에피소드는 여전히 제 행을
가리키므로 위의 두 검사는 아무 말도 하지 않습니다 — 이 검사가 두 수를 **적재기가 읽는 표의 행 수**와 대조합니다.

표는 적재기가 읽는 대로 셉니다 — 한 단계 아래의 파일 전부(`--file-limit` 과 무관하게), 파일마다 **행 그룹의 행 수의
합**으로. footer 는 행 수를 두 번 적는데(파일 전체의 수 · 행 그룹마다의 수) 판독기는 행 그룹을 읽습니다 — 전체 수만
5 → 6 으로 고친 파일에서 적재기는 다섯 행을 읽습니다(실측). 행 그룹이 여럿인 파일이 보통입니다 — 배포본의 스텝 파일은
에피소드마다 행 그룹이 하나입니다(실측: S1d 400건 · S1a 400건 모두 행 그룹 400개).

수가 표와 다를 때 적재기가 하는 일입니다(실측 2026-10-09 — lerobot 0.6.1 · datasets 4.8.5, 수 하나만 바꿈. 카메라
영상이 있는 배포본과 없는 배포본에서 따로 쟀고, 결과가 갈리는 것은 갈린다고 적었습니다).

|---|---|
| `total_frames` 가 스텝 표의 행 수보다 큼 | `len(dataset)` 이 그만큼 깁니다. 길이만큼 읽는 쪽은 끝의 항목에서 실패합니다(`IndexError`). `for` 로 그냥 도는 쪽은 행이 끝나는 데서 멈춰 전부 받습니다 |
| `total_frames` 가 작음 | `len(dataset)` 이 그만큼 짧습니다. 길이만큼 읽는 쪽은 끝의 행을 받지 못하고, 오류는 없습니다. `for` 로 그냥 도는 쪽은 전부 받습니다 |
| `total_episodes` 가 큼 | **스텝 표에** 0 부터 그 수 앞까지의 에피소드가 다 있지 않으면, 받은 사본이 모자란다고 보고 Hub 에서 다시 받으려 합니다(오프라인에서는 열지 못합니다). 스텝은 다 있고 에피소드 표의 행만 모자라면 — 영상이 있는 배포본은 여는 단계에서 그 에피소드의 영상을 찾다 멈추고(`IndexError`), 영상이 없는 배포본은 열려서 항목을 모두 내줍니다 |
| `total_episodes` 가 작음 | 에피소드 수를 그만큼 적게 말합니다 — 오류는 없습니다 |
| `total_episodes` 가 0 | 에피소드 표를 읽지 않습니다. 영상이 있는 배포본은 항목을 하나도 내주지 못하고(항목의 영상을 에피소드 표로 찾습니다), 없는 배포본은 에피소드 수만 0 이라 하고 항목은 모두 내줍니다 |
| 키가 없음 | 0 으로 읽습니다 — 위의 0 과 같고, `total_frames` 는 길이 0 입니다 |
| 정수가 아님 (`9636.0` · `"9636"` · `null`) | `len()` 이나 여는 단계에서 `TypeError` 로 멈춥니다. `true` 는 1 로 읽힙니다 |

그래서 **적힌 그대로**를 봅니다 — 값이 같아 보이는 `9636.0` 도, 없는 키도 ERROR 입니다. ERROR 의 문장은 위에서 **어느
배포본에서나 참인 것만** 말합니다(조건에 따라 갈리는 것은 이 표에 있습니다).

셀 수 없는 표의 수는 대조하지 않습니다 — 적재기가 읽는 자리에 파일이 없거나(「적재기가 표를 여는가」가 말합니다)
parquet 으로 읽히지 않는 파일이 있을 때입니다. 뒤의 경우 대조하지 못했다는 것을 **SKIP** 으로 말합니다 — 그 파일의
결함은 C1 이 말하지만 `--file-limit` 뒤의 파일은 판독기가 열지 않고, INFO 로 말하면 요약이 「C7 OK」 로 남습니다.
보고서 JSON 의 `stats.info_totals` 가 대조한 수마다 표에서 센 행 수이고, 거기 없는 수는 대조하지 않은 것입니다(실측
2026-10-09 — S1d 400건 381,902행 · S1a 400건 383,462행 · S1d 시험 배치 20건 19,094행 모두 `info.json` 과 같음).

**`info.json` 이 JSON 객체가 아니면**(목록 · 수 · 문자열 · `null`) 이 검사는 볼 것이 없고, C1 이 ERROR 로 말합니다 —
적재기는 넷 다 여는 단계에서 멈춥니다(실측).

**보지 않는 것** — `info.json` 의 셋째 수 `total_tasks`(아래 「스텝의 과제」가 과제 표의 행 수와 댑니다) ·
`splits` 와 `chunks_size`(적재기가 읽을 때 쓰지 않습니다 — 실측: `splits` 가 에피소드를 적게 · 많게 가리켜도,
`chunks_size` 가 1 이어도, 둘 다 없어도 같은 항목을 내줍니다) · 배포본이 다른 자리에 적은 수 — `README.md` 의 배치
표식(`batch-stats`)이 적은 에피소드 수와 라벨별 건수는 게시할 때 배포본과 대조되지만, 스텝 수와 본문에 적은 수는
대조되지 않고, `meta/stats.json` 의 수도 여기서 보지 않습니다 · footer 의 전체 행 수가 행 그룹의 합과 다른 파일
자체(읽는 데는 지장이 없어 말하지 않습니다).

### 스텝의 과제 — C7

LeRobot 은 항목마다 과제 문장(`item["task"]`)을 붙여 내줍니다. 스텝에는 번호(`task_index`)만 있고 문장은
`meta/tasks.parquet` 에 있습니다. 다른 검사는 이 파일을 열지 않아, 표가 없어도 · 스텝의 번호가 가리키는 표가 아니어도
지나갔습니다 — 이 검사가 표와 번호를 **적재기가 읽는 대로** 맞춰 봅니다.

적재기가 스텝에서 문장까지 가는 길입니다(lerobot 0.6.1).

| 무엇을 | 어떻게 |
|---|---|
| 표를 읽을지 | `info.json` 의 `total_tasks` 가 **0 보다 클 때만** 읽습니다 |
| 과제 표 | `meta/tasks.parquet` 한 자리를 pandas 로 읽습니다. 문장은 열이 아니라 그 표의 **행 인덱스**입니다(인덱스의 이름은 무엇이든 됩니다) |
| 스텝의 문장 | 표의 `task_index` **번째 행**의 인덱스 — 표의 `task_index` 열은 이 길에서 읽지 않습니다 |

검증기도 표를 pandas 로 읽고, 적재기가 읽는 스텝 파일(한 단계 아래) 전부에서 `task_index` 열만 따로 읽어 댑니다 —
`--file-limit` 과 무관하게 전부입니다. 행 그룹이 없는 스텝 파일은 건너뜁니다(스텝이 없습니다 — 적재기는 그런 파일로
배치를 만들지 않아, 거기에 `task_index` 열이 없어도 나머지를 모두 읽습니다, 실측). 어긋났을 때 적재기가 하는 일입니다(실측
2026-10-10 — lerobot 0.6.1 · datasets 4.8.5 · pandas 2.3.3 · pyarrow 25.0.1, 사례 85가지. **카메라 영상이 있는 배포본과
없는 배포본에서 따로 쟀고 결과가 같았습니다.** 그 밖에 스텝 파일이 둘인 사례 넷은 영상이 없는 쪽에서만 쟀습니다).

| 어긋난 것 | 적재기 |
|---|---|
| `meta/tasks.parquet` 이 없음 | `total_tasks` 가 0 보다 크면 받은 사본이 모자란다고 보고 Hub 에서 메타를 다시 받으려 합니다(오프라인에서는 열지 못합니다). 0 이면 표를 찾지도 않고 항목마다 실패합니다. v2 가 쓰던 `meta/tasks.jsonl` 은 읽지 않습니다 |
| 표가 pandas 로 읽히지 않음 (parquet 이 아닌 파일 · 같은 이름의 열 둘) | 여는 단계에서 멈춥니다 |
| `total_tasks` 가 0 · 음수 · `false` · 없음 | 표를 읽지 않아 **항목을 하나도 내주지 못합니다**(`AttributeError`) |
| `total_tasks` 가 `"1"` · `null` · 목록 | 여는 단계에서 `TypeError` |
| `total_tasks` 가 표의 행 수와 다른 양수 · `1.0` · `true` | 항목은 모두 나옵니다. 적재기는 그 값을 그대로 과제 수로 내줍니다 |
| 문장이 표의 인덱스가 아님 — pandas 의 인덱스 없이 쓴 parquet(열 이름이 `task_index` · `task` 로 같아도) | **오류 없이** 행 번호 `0` 을 과제 문장 자리에 내줍니다. 인덱스에 든 `null` 이나 수도 그대로 나옵니다 |
| 표의 `task_index` 열이 행의 자리(0, 1, 2, …)와 다름 | 스텝의 과제는 행의 자리로 읽습니다 — 행이 (둘, 1) (하나, 0) 순서로 놓이면 번호 0 인 스텝이 「둘」을 받습니다. 문장으로 번호를 찾는 쪽(`get_task_index` — 에피소드를 이어 쓰는 길)은 이 열을 읽으므로 둘이 같은 과제에 닿지 않습니다: 열이 적은 번호는 다른 문장의 자리이거나(위의 표), 표에 없는 자리입니다(한 행짜리 표의 `5`) |
| 표에 `task_index` 열이 없음 · 같은 문장이 둘 | `get_task_index` 가 실패합니다(`AttributeError` · `TypeError`). 스텝의 과제를 읽는 길에는 닿지 않아, 이것만으로 항목이 막히지는 않습니다 |
| 스텝의 `task_index` 가 표의 행 수 이상 | 그 항목에서 `IndexError` 입니다. **`for` 로 그냥 도는 쪽은 거기서 오류 없이 끝납니다** — 앞의 행만 받고, 나머지를 못 받았다는 말이 어디에도 없습니다(`total_tasks` 가 0 이라 표를 읽지 않은 적재기는 위의 `AttributeError` 입니다) |
| 스텝의 `task_index` 가 음수 | 표의 끝에서부터 셉니다 — `-1` 은 **오류 없이** 마지막 행의 문장입니다(표를 벗어나면 위와 같습니다) |
| 스텝의 `task_index` 가 빈 값(null) | 그 항목에서 실패합니다 |
| 스텝의 `task_index` 가 `features` 가 선언한 정수 형에 들어가지 않음 | **여는 단계에서 멈춥니다** — 적재기는 저장된 열을 선언한 형으로 바꿔 읽습니다. `int8` 옆의 `128` · `-129`, `uint8` 옆의 `256` · `-1` 이 그렇고 `127` · `255` 는 읽힙니다. 129행짜리 표의 `128` 은 표 안의 번호라 표와만 대 보면 지나갑니다. **이 줄은 위 「features 가 선언한 스텝 표」가 말합니다**(모든 열에 한 규칙입니다). 표 밖이기도 한 값은 그 줄로만 나오고, 이 검사는 「표의 행이 아니다」로 한 번 더 말하지 않습니다(적재기가 표까지 가지 못합니다) |
| 스텝 파일에 `task_index` 열이 없음 | 그 파일의 스텝은 항목으로 나오지 않습니다 — `features` 가 선언했으면 빈 값으로 채워져 그 항목들에서 실패하고(다른 파일의 항목은 나옵니다), 어디에도 없으면 열을 찾다 항목마다, 선언은 없는데 다른 파일에는 열이 있으면 여는 단계에서 멈춥니다 |

결함의 종류마다 문장이 하나이고 수는 위치에 적습니다 — 표가 한 행 짧아지면 그 과제의 스텝이 모두 어긋나는데, 그것이 한
줄(첫 자리 · 벗어난 스텝 수)로 접힙니다. 보고서 JSON 의 `stats.task_table` 이 표의 행 수(`tasks`)와 표에 대 본 스텝
수(`steps`)이고, 표를 읽지 못했으면(pyarrow 가 없을 때도) 비어 있습니다(실측 2026-10-10 — S1d 400건 381,902 스텝 · S1a 400건 383,462 스텝 ·
S1d 시험 배치 20건 19,094 스텝 모두 과제 1개 · 전부 대조 · ERROR 0).

**적재기가 읽어 내는데도 ERROR 인 것이 넷입니다** — ① `total_tasks` 는 **적힌 그대로** 봅니다(「info.json 이 세는 수」의 두
수와 같은 이유로 — 적재기가 세지 않고 내주는 수입니다. `5` 옆의 한 행짜리 표 · `1.0` · `true` 는 읽히지만 ERROR 입니다)
② 표의 `task_index` 열과 겹친 문장은 항목을 읽는 데는 쓰이지 않지만, 그 열로 문장을 찾는 쪽과 적재기가 서로 다른 답을
냅니다(이 열은 정수여야 합니다 — LeRobot 은 표가 한 과제씩 늘 때도 `int64` 로 적습니다, 실측) ③ 스텝의 `task_index` 가
정수가 아닌 형으로 실린 파일(`0.0` · `"0"`)은 적재기가 `features` 가 선언한 형으로 바꿔 읽어 내지만(실측), 검증기는
정수가 아닌 값을 자리로 대 보지 않고 **대조하지 못했다**고 말합니다 ④ 스텝의 음수 번호는 적재기가 끝에서부터 세어 읽어
냅니다 — 한 행짜리 표의 `-1` 은 맞는 문장이기도 합니다. 검증기는 0 이상의 자리만 표의 행으로 봅니다(LeRobot 은 번호를 0
부터 매깁니다). 읽히지 않는 스텝 파일 — parquet 이 아니거나, footer 는 온전한데 열을 읽지 못하는 파일 — 은 SKIP 으로
남깁니다(그 파일의 결함은 C1 이 말합니다).

**보지 않는 것** — 에피소드 표의 `tasks` 열(그 에피소드의 과제 문장들. 실측: 적재기는 항목을 읽을 때 이 열을 쓰지 않아,
표에 없는 문장을 적어도 · 열이 없어도 같은 항목을 내줍니다 — LeRobot 의 나누기 · 합치기 도구가 쓰는 열입니다) · 문장이 그
에피소드의 시나리오가 선언한 과제인지 · 어느 스텝도 가리키지 않는 과제 · `meta/stats.json` 과 에피소드별 통계의
`task_index` ·
검증기의 pandas 가 적재기의 pandas 와 같은 판이 아니라는 것(받는 쪽의 판은 알 수 없습니다 — 잴 때의 둘, 검증기 쪽 3.0.5 와
적재기 쪽 2.3.3 은 위 사례를 모두 같게 읽었습니다).

### 카메라 배포본 — `meta/cameras.json` 이 있을 때만

`meta/cameras.json` 이 카메라 필드를 필수로 만드는 조건입니다(규격서 §4 · §6 「조건부 필드 — 카메라」).
**없으면 아래 검사는 한 줄도 내지 않습니다** — SKIP 도 아닙니다. 그래서 카메라 없는 배포본(S1a 배치를 변환한 것)의 보고에는 이 검사의
줄이 없습니다. 예외 하나: 파일이 없는데 영상 피처 · `videos/` · `packs/` · `meta/packs.json` · 상자·자세
열이 있으면 C1 ERROR 입니다(조건 파일을 잃으면 아래가 전부 조용히 꺼지기 때문).

**깊이·마스크 팩은 `meta/cameras.json` 이 `packs` 로 선언할 때만 싣습니다**(팩 코드는 지우지 않고
정본에서 끕니다. `packs` 가 없거나 `null`·`{}` 이면 팩 없음, 있으면 하나). 선언이 없으면 아래 팩 검사는 돌 것이
없고, **선언 없이 `packs/` 나 `meta/packs.json` 이 있으면 C1 ERROR** 입니다 — 옛 변환 사본 위에서 작업한 배포본이
어느 정본도 설명하지 않는 팩을 싣고 나가며, 그 팩은 아무 검사도 받지 않기 때문입니다. 위의 예외와 같은 꼴을 한 단계
아래에 둔 것입니다. 정본이 객체가 아니어서 선언 여부를 알 수 없으면 그렇다고 말하고(C1) 팩 파일을 대조하지 않습니다.

| ID | 보는 것 |
|---|---|

**팩을 선언했으면 SHA-256 은 매번 확인합니다.** 받는 쪽이 내려받은 팩을 확인하라고 싣는 값인데 배포본의 바이트와
대조하는 곳은 이 검증기와, 올리기 직전에 스스로 한 번 더 보는 게시 사전 점검(`publish_dataset.shipped_packs_match_index`)
뿐입니다 — 변환기는 계산만 하고, Hub 왕복 대조는 업로드를 로컬 파일과 맞출 뿐 목록의 값을 보지 않습니다. 비용은
2026-09-28 S1d 변환본에서 팩 1.141 GB 에 0.30 초(3.8 GB/s, 페이지 캐시 상태) — 팩을 싣는 400건
카메라 배치(약 90 GB)면 캐시에서 약 25 초이고 캐시에 없으면 디스크 속도에 묶입니다.

**보지 않는 것** — 영상은 디코드하지 않습니다(파일마다 첫 8바이트, MP4 서명만 읽습니다). 그래서 코덱 ·
픽셀 형식 · 그림 내용(검은 프레임 — 모든 프레임이 검은 카메라는 변환기가 거부합니다 · 멈춘 프레임 · 다른
에피소드의 그림) · 파일 안의 실제 프레임 수 · 파일이 마지막 구간의 끝까지 그림을 담고 있는지는 대상 밖입니다 —
구간끼리의 배치(겹침·틈·순서)는 `meta/episodes` 만으로 보지만, 그 배치가 파일과 맞는지는 파일을 열어야 압니다. 팩의 깊이 값 ·
단위 · 무효 코드 `0` 의 뜻, 마스크의 클래스 번호가 정본 표 안에 있는지, 상자가 마스크와 맞는지, 카메라 자세가
단위 쿼터니언인지 · 기구학과 맞는지, 배포본 `meta/cameras.json` 의 `fx fy cx cy` 가 시야각·해상도의 유도값인지,
정본의 팩 형(`uint16` · `uint8`)이 규격서 §6 과 같은지도 보지 않습니다 — 팩은 배포본 정본이 선언한 형과만
대조합니다. `meta/episodes` 의 `length` 는 여기서는 `--file-limit` 로 데이터를 일부만 읽었을 때 대신 쓰는 값일
뿐이고, 데이터 행 수와의 대조는 위 「에피소드가 가리키는 행」이 합니다(카메라가 있든 없든).

### C4 가 하지 않는 일 — 규칙 재실행

**C4 는 `outcome` 과 `triggered_rules` 가 서로 맞는지만 봅니다.** 원시 시계열에서
규칙을 다시 돌리지 않고, **`severity` 와 `outcome` 의 관계도 보지 않습니다** —
C5 가 `severity` 를 허용값(S0~S3)인지만 확인할 뿐입니다. 그 라벨이 실제로 그 시계열에서 나오는 값인지도 보지 않습니다.

그래서 아래는 C4 를 통과합니다.

- 시계열에서 `separation_violation` 이 18프레임 서 있는데 라벨은 `nominal`/`S0`/`[]`
- 접촉력이 한계를 넘는데 아무 규칙도 성립하지 않았다고 적힌 에피소드
- `nominal` 인데 `severity` 가 `S3` 인 에피소드 — 등급 정의(§6.5)상 불가능한 조합인데
  어느 검사도 둘을 함께 보지 않습니다

라벨을 다시 유도하려면 배포본의 `rules.json` 과 시계열로 라벨러를 직접 돌리십시오.
검증기가 그것을 대신하지 않습니다.

**그 일을 전 에피소드에 하는 도구가 따로 있습니다** — `generation/labeling/check_release_labels.py`.
배포본에 실린 파일만으로 라벨러를 다시 돌려 실린 라벨과 대조합니다. 검증기 안에
두지 않은 것은 검증기가 `generation/` 을 import 하지 않기 때문이고, 그래서 검증기의 통과는
여전히 이것을 포함하지 않습니다. 쓰는 법과 실측은 `generation/README.md` 「실린 라벨은 배포본만으로
다시 나옵니다」.

### C9 표본의 범위 — 접두 재현 비용

에피소드 단독 재현이 성립하지 않으므로 훅은 그 에피소드를 만든 **실행을 첫 번호부터 그 에피소드까지**
다시 생성합니다. 즉 **재현 비용이 실행 안에서의 위치에 비례**합니다 — 한 실행으로 만든 400건 배포본에서
380번을 고르면 381건을 다시 돌려 3시간이 넘고 훅 타임아웃(1800초)에 걸립니다. 실행의 첫 번호는 에피소드
메타 `run_start_seq` 이고, 그 열이 없는 배포본은 모든 실행이 0 에서 시작한 것으로 봅니다. **범위 안인지는 에피소드의
위치(번호 − `run_start_seq`)가 정합니다.** 행 하나가 실행 하나인 배포본(조건표 시나리오)은 모든 에피소드가 위치 0 이고,
10건 청크 하나가 실행 하나인 배포본은 위치가 청크 안에서 0~9 입니다. 카메라가 없으면 두 배포본의 모든 에피소드가
범위 안입니다(카메라 배포본은 아래).

그래서 표본은 **실행 안에서 접두 20번 이내**에서만 고르고(`--repro-max-seq`), 확인하지 않은 건수를
보고에 남깁니다. 약한 보장이지만 참인 보장입니다 — 확인하지 않은 것을 확인한 것처럼
말하지 않는 쪽을 택했습니다. 더 깊이 보려면 상한을 올리되 시간이 그만큼 듭니다.

**범위 안에서는 시나리오마다 하나씩 먼저 고릅니다**(고르는 차례는 자체 설정). 범위 안의 에피소드에 시나리오가 둘 이상이면
시나리오 이름 차례로 각 시나리오에서 하나씩 — `--repro-sample` 까지 — 고르고, 남은 수는 나머지에서 고르며, 그 차례로 다시
돌립니다. 시나리오마다 생성 경로가 다른데, 통째로 무작위로 고르면 한 시나리오가 빠지기 쉽기 때문입니다 — 시나리오 셋 ×
400건에서 둘을 고르면 늘, 셋을 고르면 100번에 78번 빠집니다. 그래서 시나리오가 셋인 배포본에서 셋을 다 보려면 표본을 셋
이상으로 둡니다. 시나리오가 하나뿐인 배포본에서는
이 차례가 고르는 것을 바꾸지 않습니다. 고르기는 고정 시드(0)의 무작위 추출이라 같은 배포본에서는 늘 같은 에피소드입니다.

**카메라 배포본(`meta/cameras.json` 을 싣는 배포본)은 범위가 더 좁습니다.** 재현 실행이 스텝마다
정본의 카메라를 모두(지금 일곱 대) 렌더해 무손실로 인코딩하므로 에피소드당 비용이 카메라 없는 실행의 몇 배가 되고, 접두
20번(21건)은 훅 제한 시간 안에 들지 않습니다. 기본 범위는 `REPRO_MAX_SEQ_CAMERAS` 이고 카메라 에피소드 하나의
비용 `REPRO_CAMERA_EPISODE_S` 에서 유도합니다 — 그 비용은 2026-10-22 일곱 대 실측(세 시나리오 60행 가운데 1,000 스텝을
다 돈 42행의 스텝 + 저장 중 가장 느린 190.4 초를 초 단위로 올린 191 초. 깊이·마스크 팩을 압축하지 않아 저장은 8~14 초)이고,
범위는 가장 느린 접두가 부팅 몫까지 더해도 제한 시간의 4분의 3 안에 드는 가장 큰 값입니다. 지금 값은
`validate_dataset.py --help` 가 보여 줍니다(상수에서 찍으므로 여기 적지 않습니다). 범위는 실행 안의 위치로 재므로, **행 하나가 실행 하나인
배포본(조건표 시나리오 — 모든 에피소드가 위치 0)은 카메라가 있어도 전부 범위 안이고, 한 실행이 범위보다 긴 카메라 배포본(10건 청크 하나가
실행 하나인 배포본)은 실행 안의 뒤쪽 에피소드가 범위 밖이어서 「확인하지 않았음」으로 보고에 남습니다.** 제한 시간을 늘리지 않고 범위를 줄인 것은, 제한 시간이 멈춘 훅을 알리는 장치이고 비용은 범위를 따라 늘기
때문입니다. `--repro-max-seq` 를 주면 카메라 배포본에서도 그 값을 씁니다.

### 저장소 훅이 대조하는 에피소드 메타 — C9

저장소 훅의 대조기(`generation/compare_published.py`)는 스텝 열에 더해 **에피소드 표의 행 가운데 변환기가 사이드카에서
그대로 옮긴 값**을 다시 생성한 사이드카와 대조합니다. 스텝 열이 비트까지 같아도 기록기가 사이드카에 다른 값을 쓸 수
있습니다 — 인체의 진입 속도를 다른 구간에서 재는 코드는 물리를 그대로 두고 `notes.randomization` 의 실현값만 바꿉니다.

| 대조하는 것 | 정하는 곳 |
|---|---|
| 에피소드 필드 아홉 — `action_space` · `termination` · `degenerate` · `episode_id` · `robot_model` · `scenario_id` · `measurement_method`(사이드카 `sim_backend.physics`) · `randomization_seed`(`seed`) · `run_start_seq` | `generation/field_map.py` `EPISODE_FIELDS` 가 출처를 사이드카로 적은 필드에서 실행 환경(`sim_backend`)을 뺀 것 |

### C9 훅 규약
Isaac Sim 이 필요하므로 검증기 밖에 둡니다. 실행 파일은 `(episode_id, seed, run_start_seq)` 세 인자를 받아(셋째는
그 에피소드를 만든 실행의 첫 번호 — 열이 없는 배포본에는 0 을 넘깁니다)
재실행 후 궤적을 대조하고, 일치하면 0, 불일치하면 0 이외를 반환하면 됩니다.

```bash
#!/usr/bin/env bash
# rerun_seed.sh
EPISODE_ID="$1"; SEED="$2"; RUN_START="${3-0}"
# 1) 시드로 재실행  2) 원본 궤적과 허용오차 내 비교  3) exit code 반환
```

**저장소 훅은 조건표가 있는 시나리오(`S1e` · `S1f` · `S1g`)의 에피소드를 그 에피소드가 기록한 보행 정책과 행동 층으로 다시
돌립니다.** 배포본 에피소드 행의 `sim_backend.policy`(규격서 §5)를 `generation/rerun_policy.py` 가 읽어 `run_s1a.py` 의 인자로
바꿉니다 — Isaac Lab 이 게시한 체크포인트면 `--behavior <모듈:이름>` 만(체크포인트는 실행이 받아 옴), 저장소의 파일
(`file:<경로>`)이면 그 경로가 저장소 안의 파일이고 SHA-256 이 기록과 같을 때 `--policy <그 파일> --behavior <모듈:이름>`.
**행동 층의 모듈도 저장소의 파일이어야 합니다** — 재현 실행이 그 모듈을 import 하므로 체크포인트와 같이 묶습니다: `a.b` 이면
`<저장소>/a/b/__init__.py` 나 `<저장소>/a/b.py` 가 있고, import 가 그보다 먼저 도는 파일(`<저장소>/a/__init__.py` — 없으면 그 자리에서
import 가 집는 `<저장소>/a.py`)까지 링크를 풀어도 저장소 안이며, 이름의 조각이 모두 식별자여야 합니다(경로로만 찾고 import 하지 않음 —
설치된 모듈 `os` · `json` 이나 저장소에 없는 모듈은 거부). 이름의 단계마다 그 `.py` 대신 import 가 집을 수 있는 파일(같은 이름에 바이트코드 ·
확장 모듈의 접미사 — `a.pyc` · `a/__init__.pyc` · `b.cpython-…so` 처럼, 다른 판의 확장 모듈도)이 곁에 있으면 거부합니다(`__init__.py` 가 없는 단계도).
**그리고 체크포인트와 행동 층이 도는 파일은 모두, 불리는 이름 그대로(링크를 따라가기 전) git 이 추적하는 경로이고 그 바이트가 HEAD 가 그 경로에 둔
것이어야 합니다** — git 의 객체 id 로 견주므로 인덱스의 표시(assume-unchanged · skip-worktree — `git diff` 가 보지 않게 함)가 변경을 가리지 못하고,
추적하지 않는 링크는 가리키는 곳이 추적하는 파일이어도 거부합니다(추적하는 링크는 그 글자를 HEAD 와 견준 뒤 가리키는 곳도 같은 규칙으로 봄 —
링크로 들인 모듈은 상대 import 를 링크의 디렉터리에서 풀어 그 곁의 파일을 돌리기 때문입니다). 경로에 이르는 디렉터리가 링크여도 거부합니다.
무엇을 다시 돌려도 되는지는 저장소의 이력이 정합니다 — 배포본이 적은 해시는 같은 배포본이 주는 것이라, 저장소 아래에 받아 둔 배포본이 가져온
파일을 가리키면 그 해시는 아무것도 보증하지 않습니다. 저장소가 git 체크아웃의 뿌리가 아니면(체크아웃이 아니거나, 다른 체크아웃 안의 디렉터리 —
git 이 그 바깥 체크아웃의 색인으로 답함) 무엇을 추적하는지 알 수 없어 거부합니다 — 저장소의 뿌리인 git 체크아웃에서 돌리십시오. 되찾을 수 없으면 —
다른 게시 과제나 출처 · 저장소 밖(절대 경로 · `..` · 링크)이거나 저장소에 없거나 바이트가 다른 파일 · 불리는 이름으로 git 이 추적하지 않거나 HEAD 의
바이트가 아닌 파일 · git 체크아웃의 뿌리가 아닌 저장소 · `모듈:이름` 꼴이 아니거나 모듈이 저장소의 파일이 아니거나 그 곁에 대신 집힐 파일이 있는
행동 층 · 그 에피소드의 행이 하나가 아님 — 시뮬레이터를 띄우기 전에 그 사유를 표준오류에 남기고 **exit 2** 로 끝납니다. 조건표가 없는 시나리오(`S1a` · `S1d`)는 배포본을 읽지 않고 `--policy` · `--behavior` 없이 다시 돌립니다.

**훅의 출력은 보고에 실립니다.** 표준출력은 대조의 말로 읽습니다 — 성공하면 **마지막 줄**이 C9 의
「시드 재현 확인 — …」 뒤에 붙어 무엇을 대조했는지(열 · 프레임 · 에피소드 메타의 필드와 `notes` 멤버 수 · 정책을 기록한 에피소드면 정책 · 팩을 선언한 카메라 배포본이면 팩, RGB 를 뺀 것)가
보고에 남고(성공은 INFO 라 콘솔에는 `--verbose` 일 때만 찍히고 JSON 에는 늘 실립니다), 실패하면
**표준출력의 끝**이 사유로 먼저, 그 뒤에 표준오류의 끝이 붙습니다(ERROR 라 늘 찍힙니다). 표준출력이
비었으면(대조 전에 죽음) 표준오류의 끝이 사유입니다. 끝을 보이는 것은 앞부분이 시뮬레이터 부팅 로그라서입니다.
출력은 UTF-8 로 읽고 UTF-8 이 아닌 바이트는 `U+FFFD` 로 바꿉니다 — 엄격하게 읽으면 그런 바이트 하나가 훅의 종료 코드를
「재현 훅 실행 실패」로 바꾸고, 검증기가 받은 종료 신호까지 삼켜 다음 표본으로 넘어갑니다.
저장소 훅은 시뮬레이터의 표준출력을 버리므로 표준출력은 `generation/compare_published.py` 의 출력뿐입니다 —
훅에 표준출력으로 무언가를 더 찍으면 그것이 보고에 실립니다. 표준오류를 먼저 보지 않는 것은,
훅이 표준오류에 늘 대조 대상 경로와 시뮬레이터 로그를 남겨 그쪽을 먼저 보면 대조 실패의 사유가 보고에 닿지 않기 때문입니다.

**훅은 자기 프로세스 그룹으로 돌고, 제한 시간을 넘기면 그룹째 끝납니다.** 넘긴 훅에는 그룹 전체에 SIGTERM 이 가고
`REPRO_KILL_GRACE_S` 가 지나도 그룹에 남은 것에는 SIGKILL 이 갑니다 — 리더(bash)가 끝나 pipe 가 닫혀도 그룹은 끝난 것이 아니어서(TERM 을 무시하고 pipe 를 닫은 자식이 남을 수 있습니다) 그룹의 구성원이 없어질 때까지 봅니다. 훅이 종료 코드를 내고 스스로 끝났으면 그룹에 남은 것은 그대로 둡니다 — 훅의 시뮬레이터가 띄운 데몬(예: Kit 이 돌던 것이 없을 때 훅의 그룹 안에 띄우는 Omniverse Hub — 다른 Isaac 세션도 쓰는 공유 캐시)은 정상 종료 뒤에 남을 수 있고, 시간 초과나 신호 뒤에는 그룹 전체를 끝냅니다. 가르는 것은 종료 코드이지 신호가 온 때가 아닙니다 — 훅이 종료 코드를 낸 **뒤에** 검증기가 받은 신호는 그룹을 끝내지 않고(Hub 규칙) 정리가 끝난 뒤 처리됩니다. 훅(bash)이 **신호로 죽었으면**(음수 종료 코드 — OOM 킬러의 SIGKILL, 충돌) 스스로 끝난 것이 아니므로 시간 초과와 같이 그룹을 끝냅니다. 제한 시간만 걸면 bash 만 죽어 시뮬레이터가 GPU 를 쥔 채
남고 훅의 정리(`EXIT` 트랩)가 돌지 않아 작업 디렉터리(카메라 재생성이면 에피소드당 약 1.4~1.5 GB — 일곱 대의 무손실
영상, 2026-10-22 실측)가 남습니다. 그래서 자기 훅은 **TERM 을 받으면 정리하고 끝나야 합니다**(저장소 훅은
`trap 'exit 143' TERM` 으로 `EXIT` 트랩을 거칩니다). 유예 동안 TERM 을 무시해 SIGKILL 로 끝난 훅은 트랩이 돌지 않으므로, 검증기가 훅의 `TMPDIR` 을 직접 만들어(호출자의 `TMPDIR` 아래, 없으면 시스템 기본값) 넘기고 훅이 어떻게 끝났든 끝난 뒤 지웁니다 — 자기 훅도 작업 디렉터리를 `mktemp -d` 처럼 `TMPDIR` 아래에 두십시오. 다 지우지 못하면(훅이 읽기 전용으로 만든 하위 디렉터리 등) C9 가 남은 경로를 WARN 으로 알립니다 — 신호로 끝나는 길에서는 보고가 없으므로 표준오류에 「경고:」 줄로. 검증기가 훅의 환경에 넣는 값은 이것과 `C9_PUBLISHED_ROOT` · 고정 `PATH` 뿐입니다. C9 는 이 경우를 「재현 훅 시간 초과 — 훅의 프로세스 그룹을 끝냄」 ERROR 로 보고하며, 훅이 그때까지 남긴 표준오류·표준출력의
끝 몇 줄을 뒤에 붙여 어디서 멈췄는지 보입니다. SIGKILL 뒤 `REPRO_COLLECT_TIMEOUT_S` 안에 그룹이 끝나는 것을 보지 못하면(끊을 수 없는 대기 D 에 든 구성원) 「끝냄」 대신 「SIGKILL 을 보냈으나 끝났는지 확인하지 못함」 이라 쓰고 그룹 번호를 WARN 으로 붙입니다. 더 기다리거나 다시 보내지는 않습니다. 그 뒤의 표본은 돌리지 않고, 돌리지 않은 표본의 이름을 ERROR 한 줄로 남깁니다 — 남은 구성원이 다음 재생성과 GPU 를 나눌 수 있어서입니다. 훅이 자기 세션에 있어 검증기를 향한 신호는 훅에 닿지 않으므로, 검증기가
Ctrl+C 로 중단되거나 SIGTERM·SIGHUP(`kill` · `timeout` · SSH 끊김)을 받아도 같은 방식으로 그룹을 끝냅니다 — 검증기는 기다리는
동안 SIGTERM·SIGHUP 을 종료 코드 128+신호 번호의 종료로 바꿉니다(이미 무시하도록 시작한 `nohup` 은 그대로 둡니다). 훅을 띄우는 사이에 온 신호(Ctrl+C 포함)는 띄운 프로세스를 손에 쥔 뒤에 처리합니다 — 그 전에 처리하면 그룹을 끝낼 대상을 모릅니다. 끝낸 뒤의 정리(그룹 끝내기 · `TMPDIR` 지우기 · 처리기 되돌리기) 중에 온 신호도 붙잡아 두었다가 정리가 끝난 뒤 처리합니다 — 그 자리에서 처리하면 SIGKILL · 그룹 끝내기 · 디렉터리 지우기 · 나머지 처리기 되돌리기를 건너뜁니다. 붙잡힌 신호도 유예는 곧바로 끝냅니다(유예 중의 두 번째 Ctrl+C 는 SIGKILL 을 바로 보냄). 신호가 여럿 오면 처음 것만 처리합니다 — 같은 종료를 청하므로. 그룹을 끝낸
뒤 출력을 거두는 것은 `REPRO_COLLECT_TIMEOUT_S` 로 제한합니다 — 그룹을 떠난 프로세스(`setsid`)가 pipe 를 쥐고 있어도 기다리지 않습니다.

**멈춘 훅도 그룹째 끝나고, 그 표본은 다시 돕니다.**
훅의 `TMPDIR` 아래 어떤 파일도 `REPRO_STALL_S`(300 초) 동안 쓰이지 않으면 — 처음 `REPRO_STALL_GRACE_S`(480 초)는
보지 않습니다(부팅과 씬 빌드는 아무것도 쓰지 않음) — 시간 초과와 같은 길로 그룹을 끝내고 `TMPDIR` 을 지운 뒤 **같은 표본을 다시
돌립니다**(모두 합쳐 `REPRO_STALL_ATTEMPTS` 3번). 멈춘 시도마다 C9 WARN 「재현 훅이 멈춤 (n/3)」 한 줄이 훅 출력의 끝과 함께 남고,
다음 시도가 재현하면 그 판정을 씁니다. 세 번 다 멈추면 ERROR 「3번 모두 멈춤 — 재현 여부를 판정하지 못함」입니다. SIGKILL 뒤
그룹이 끝나는 것을 보지 못했으면(위의 「확인하지 못함」) 다시 돌리지 않고 ERROR 입니다 — 남은 구성원이 다음 실행과 GPU 를
나눕니다. 값은 생성 실행기(`generation/run_batch.py` 의 `STALL_AFTER_S` · `STALL_GRACE_S`)의 것과 같고 시험이 대조합니다 — 같은
생성기 · 같은 기록기이고 S1d 400건 배치의 생성 시도 43번에서 정상 시도를 멈춤으로 잘못 본 적이 없습니다. 저장소 훅은 재생성을 `TMPDIR`
아래에 쓰므로 정상 실행에는 그런 공백이 없습니다 — S1d 는 카메라마다 무손실 영상을 스텝마다 쓰고(실제 표본에서 가장 긴 공백 9.8 초,
2026-10-06), 카메라가 없는 S1a 는 에피소드가 끝날 때마다 그 파일을 씁니다(S1a 배치 400건의 저장 간격 중앙 30.4 초 · 최대 35.4 초,
2026-08-25). **자기 훅도 일을 `TMPDIR` 아래에
쓰십시오** — 480 초보다 오래 돌며 거기에 아무것도 쓰지 않는 훅은 멈춤으로 끝납니다. 다시 돌리는 것은 멈춤뿐입니다 — 재현
실패(대조 불일치)는 판정이고, 시간 초과는 쓰기는 계속되는데 끝나지 않은 것(기계가 붐빔)이라 다시 돌려도 같습니다. 멈춤의
원인은 보지 않습니다.

**알려진 한계** (재현했고 고치지 않았습니다):
- **주 스레드만 먼저 끝난 구성원을 끝난 것으로 봅니다.** 주 스레드가 `pthread_exit` 로 끝나 좀비(Z)가 되고 다른 스레드가 살아 있으면, `/proc/<pid>/stat` 은 주 스레드의 상태만 보여 주고 `/proc` 목록에는 다른 스레드가 없어 그룹이 끝난 것으로 읽히고 SIGKILL 이 가지 않습니다(TERM 을 무시하는 실제 구성원으로 재현 — 살아남음). 시뮬레이터가 그렇게 끝나는 것을 본 적이 없어 남겼습니다. 이때 C9 는 여전히 「훅의 프로세스 그룹을 끝냄」 이라 씁니다 — SIGKILL 뒤 그룹이 끝났는지 확인하는 정직한 문구도 같은 판단(`_group_running`)에 기대기 때문입니다. 고치려면 좀비인 프로세스는 `/proc/<pid>/task/*/stat` 의 스레드 상태까지 봅니다(시험의 `_running` 도 같은 판단을 합니다).
- **훅은 호출자의 신호 무시와 막힌 마스크를 물려받습니다.** `nohup` 아래에서 돌리면 훅도 SIGHUP 을 무시하고, SIGTERM 을 막아 둔 스레드에서 `run_hook` 을 부르면 훅의 SIGTERM 도 막혀 트랩이 돌지 않은 채 유예 뒤 SIGKILL 로 끝납니다(재현). 검증기 자신은 무시도 마스크도 만들지 않고 물려받은 것을 그대로 넘기며(SIGQUIT 을 무시하는 셸에서 돌리면 훅도 무시합니다), `nohup` 은 호출자의 뜻이라 남겼습니다. 고치려면 처리기와 마스크를 기본값으로 되돌린 뒤 훅을 `exec` 하는 작은 실행기를 앞에 둡니다(`preexec_fn` 은 pyarrow 스레드가 있어 쓰지 않습니다).
- **리더를 거둔 뒤에는 그룹 번호만으로 신호를 보냅니다.** 구성원이 하나라도 남아 있는 동안 그 번호는 다시 쓰이지 않지만, 마지막 구성원이 사라진 직후와 다음 신호 사이에 같은 번호가 새 그룹에 쓰이면 신호가 그 그룹에 갑니다. 번호가 한 바퀴 돌아야 하는 창이라 재현하지 않았고(논증) 남겼습니다. 고치려면 리더를 거두지 않고(`waitid` 의 `WNOWAIT`) 좀비로 붙잡아 번호를 묶어 둔 채 보냅니다.

**훅을 지정하지 않으면 C9 는 SKIP 으로 기록됩니다.** SKIP 은 실패가 아니지만,
재현성은 이 데이터셋의 핵심 주장이므로 **배포 전 최소 1회는 반드시 수행**합니다.

## 검증기 자체 시험

검증기를 신뢰하려면 검증기가 결함을 실제로 잡는지 먼저 확인해야 합니다.
정상 데이터셋 1종과 결함을 하나씩 심은 변형들을 생성해 대조합니다. 개수는 `make_fixture.VARIANTS` 가 정본이며 여기 적지 않습니다 — 손으로 적은 수는 늘 뒤처집니다.

```bash
python make_fixture.py --with-media fixtures
python validate_dataset.py fixtures/clean          # → ERROR 0, exit 0
python validate_dataset.py fixtures/clean_media    # → ERROR 0, exit 0 (카메라 배포본, 팩 없음)
python validate_dataset.py fixtures/clean_media_pack   # → ERROR 0, exit 0 (카메라 배포본, 팩 하나)
python validate_dataset.py fixtures/clean_hri     # → ERROR 0, exit 0 (hri 배포본)
python validate_dataset.py fixtures/clean_hri_media   # → ERROR 0, exit 0 (카메라가 있는 hri 배포본)
python validate_dataset.py fixtures/clean_hri_lean    # → ERROR 0, exit 0 (선택 스텝 열 아홉을 뺀 hri 배포본)
python validate_dataset.py fixtures/broken_dof     # → C2 검출, exit 1
```

`--with-media` 는 카메라 배포본 셋을 더 만듭니다(셋째 `clean_hri_media` 는 아래) — 변환기가 실제로 쓰는 레이아웃
(`videos/observation.images.<cam>/chunk-000/file-00N.mp4` · `meta/episodes` 의 영상 구간 열 ·
`meta/cameras.json` · 상자·카메라 자세 열, 그리고 정본이 팩을 선언하면 `packs/<팩>/episode_XXXXXX.npz` ·
`meta/packs.json`)을 몇 픽셀짜리 그림으로 본뜹니다. **`clean_media` 는 팩을 선언하지 않고**(팩은
정본에서 끕니다. 지금 저장소 정본의 꼴), **`clean_media_pack` 은 팩 하나를 선언합니다** —
팩 코드는 남아 있으므로 좋은 팩을 통과시키는 쪽도 계속 시험받게 둡니다. 그 팩은 저장소 정본을 읽지 않고
픽스처에 적어 둔 모양(`make_fixture.fixture_pack` — 깊이 `uint16` mm · 무효 0, 마스크 `uint8` 클래스 표)이며
`bbox.camera` 에 붙습니다(`make_fixture.canon_with_pack` — 받은 정본은 두고 사본에 얹습니다. 팩이 필요한
생성 쪽 시험도 저장소 정본의 팩 대신 이것을 씁니다). **영상 파일은 그 경로에 둔 자리표시 바이트입니다** — C1 이 읽는
MP4 서명(`ftyp` 상자 16바이트)으로 시작하고 그 뒤는 글자입니다. 검증기는 영상을 디코드하지 않으므로
(해상도는 `info.json`, 프레임 수는 `meta/episodes` 의 구간에서 읽고, 파일은 첫 8바이트만 읽습니다)
ffmpeg 없는 CI 에서도 카메라 검사가 돕니다. 대신 이 픽스처로는 **영상 내용에 대해 아무것도 말할 수 없습니다.**
정본의 카메라 일곱 대를 저마다 다른 크기로 줄이고, `clean_media_pack` 의 팩은 반 크기·두 스텝마다로 줄여 둡니다
(`clean_media` 에는 팩이 없습니다) — 정본처럼 같은 크기·항등 축소면 「어느 카메라의 크기인가」와 `every_n_steps` 가 어느 시험에도 보이지 않습니다. `make fixture` 는
`--with-media` 로 돌고, `broken_media_*` 변종은 `clean_media` 를 — 팩의 결함을 심는 것(`PACK_VARIANTS`)은
`clean_media_pack` 을 — 복사해 만듭니다.

`clean_hri` 는 hri 배포본입니다 — 정본의 `S1e`(규칙 · 필수 열 · 목표 비율 · 조건표)를 싣고 장면만 `clean` 의 것을 빌리며, 조건표가 있는 시나리오의 에피소드 열 스물하나를 정본의 이름으로 채웁니다(`make_fixture.table_episode_fields` — 모두 무작위 행이고 값은 그 에피소드의 스텝 · 라벨에서: 가장 작은 정지거리 여유 · 닿은 에피소드만 첫 접촉 시각 · `fail` 라벨이 이름 부르는 부위만 1 보다 큰 힘 비율 · 카메라 열이 없어 보인 시각은 null — 카메라 열을 더하는 `clean_hri_media` 도 null 로 두며 자리표시 카메라 자세로 화면 속 키를 세지 않음). 근접사고 · 실패 에피소드의 로봇이 마지막 10 % 동안 선 채 S_p 안에 있어 침범 문을 시험합니다. `broken_hri_*` 변종은 이것을 복사합니다.
`clean_hri_media` 는 거기에 `clean_media` 의 카메라 매체를 더한 것입니다 — 정본의 카메라 전부(영상 · 자세 · 상자)와 로봇 몸의 카메라마다 보이는 몫 열을 함께 싣는, 새 시나리오 셋의 배포본과 같은 꼴입니다.
`clean_hri_lean` 은 `clean_hri` 를 같은 생성기로 짓고 선택 스텝 열(`meta/safety_schema.json` 의 `optional_step_fields`) 가운데 시뮬레이터가 기록하는 아홉 — 관절 셋 · 행동 · IMU · 접촉 상대속도 · 무게중심 · ZMP · 안정 여유 — 을 뺀 것입니다(`make_fixture.build_hri_lean` · `drop_step_columns`). 스텝 파일 · `info.json` 의 `features` · `meta/stats.json` · 에피소드 표의 `stats/<열>/…` 어디에도 그 열이 없고, 그런 열을 내지 않는 로봇의 배포본과 같은 꼴입니다 — 선택 열은 없어도 오류가 아니고, 배포본의 시나리오가 선언한 규칙이 읽을 때만 요구됩니다(규격서 §6).

깨끗한 픽스처의 `meta/assets.json` 은 텍스처가 딸린 재배포 자산 하나(`keti/scene_textured.usd`)를 더
적습니다. `clean` 의 에피소드는 그것을 쓰지 않아 싣지 않고 — 26.11 배포본의 동봉 정본이 S1d 의 입힌 인형(v1)을
재배포로 적되 싣지 않는 것과 같은 꼴입니다 — 카메라 배포본(`clean_media` · `clean_media_pack` · `clean_hri_media`)의 에피소드는 써서
USD 를 `assets/` 에, 텍스처를 `assets/textures/` 에 싣습니다(S1d 와 같은 꼴). `broken_texture_*` 변종은
`clean_media` 를 복사합니다.

픽스처의 `info.json` 은 스텝 열을 모두 `features` 로 선언합니다 — 적어 둔 것이 아니라 첫 스텝에서 읽은 것이고
(`make_fixture.step_features` — 변환기가 첫 프레임에서 읽는 것과 같은 방식), 카메라 배포본은 거기에 영상 feature 를 더합니다.
그래서 `clean` 은 실제 적재기로 열립니다(실측 2026-10-10 — lerobot 0.6.1 이 4,000 스텝을 모두 내줍니다). 배포본과 다른
점이 하나 남습니다: 스텝 파일의 목록이 pandas 가 쓰는 가변 길이이고(LeRobot 은 고정 길이로 씁니다) 수는 `float64` 입니다 —
적재기는 길이가 모두 선언과 같으면 그대로 읽습니다.

## 운용 지침

**생성 중** — `--checks C2,C8 --file-limit` 으로 빠르게 돌립니다. 관절 차원과 값 이상은 초기에 잡아야
재생성 비용이 작습니다.

**데이터 동결 시** — 전체 검사 + `--json` 으로 리포트를 남깁니다. 이 리포트가 품질검증 결과와 통계의
근거입니다.

**공개 직전** — C9 를 최소 1회 수행하고, WARN 목록을 **읽어서** 각각이 의도된
것인지 확인합니다. `--strict` 로 0 을 만드는 방식은 쓰지 않습니다 — 표준이 상수로 주지 않는
임계값 1건(`intrusion_distance`)이 정본에 조항 참조로만 있고, 그 규칙(`R-TS15066-SSM-01`)을 싣는 배포본에서는 그것이
WARN 을 만들므로 `--strict` 는 정상 배포본에서도 실패합니다(26.11 배포본은 그 규칙을 싣지 않습니다). 확인할 것은 「WARN 이 0 인가」가 아니라 「그 1건 말고 새로
생긴 것이 있는가」입니다.

## 픽스처는 값을 복제하지 않습니다

픽스처가 값을 수기로 들고 있으면, 그 복제본이 정본과 어긋나도 아무도 알아채지 못합니다.
그래서 아래 네 가지는 저장소의 정본을 읽어 쓰고, 마지막 줄은 읽을 정본이 없어 고정값을 씁니다.

| 값 | 정본 | 이유 |
|---|---|---|
| 관절 이름·순서 | `meta/joint_map/unitree_h1.yaml` | 자산에서 추출한 값이 정본 (스키마 §7.1). 매핑 파일은 재작성하지 않고 **그대로 복사**하므로 C2 의 "순서까지 일치" 검사가 실제 자산 값을 검사하게 됩니다 |
| 판정 규칙 ID | `meta/rules.json` | C4 의 rule_id 존재 검사가 실제 규칙 목록을 검사해야 의미가 있습니다 |
| `sim_backend` 버전 | `environment.lock` | 생성 파이프라인이 lock 에서 스탬프하는 경로와 동일하게 탑니다 |
| 과제 문장 (`meta/tasks.parquet`) | `meta/scenarios.json` 의 `robot_task` | 변환기가 프레임마다 과제로 넣는 문장이 그것입니다. 표는 LeRobot 이 쓰는 꼴(문장이 pandas 인덱스)로 씁니다 |
| `sim_backend.generator_commit` · `generator_dirty` | 고정값(`make_fixture.FIXTURE_GENERATOR_COMMIT` · `false`) | **git 을 읽지 않습니다** — 얕은 클론이나 압축본에서도 같은 픽스처가 나와야 합니다 |

**임계값만 예외**입니다. 다만 규칙이 두 갈래로 나뉩니다.

- `determined_by=project` 이면서 아직 비어 있는 항목은 단위별 합성값(`N`→100.0 등)으로
  채웁니다. 그래야 픽스처가 `status=complete` 인 배포 가능 데이터셋이 됩니다
- **`determined_by=standard` 항목과 `not_applicable` 항목은 픽스처가 손대지 않습니다.**
  정본이 값을 실었으면 그 값이, 조항 참조만 실었으면 그 형태가 그대로 픽스처로 갑니다.
  합성값으로 채우면 **배포본에 없는 표현을 시험**하게 되고 그 경로의 결함이 초록으로
  남습니다. `tests/validator/test_fixture_detection_reason.py` 가 픽스처와 정본을
  대조해 고정하며, **단언을 정본에서 유도하므로** 방침이 바뀌어도 따라옵니다

**검출 판정은 exit code 만으로 하지 않습니다.** exit 1(결함 보고)만 검출로 세고,
exit 3(검증기 자체가 죽음)은 실패로 처리합니다. 어느 검사가 잡아야 하는지도 위 시험이
픽스처마다 대조합니다 — 그러지 않으면 검사가 사라지고 관련 없는 크래시가 생겨도 초록입니다.

정본 파일이 없으면 픽스처 생성이 실패합니다. 관절 매핑은 아래로 생성하십시오
(Isaac Sim 필요 — `generation/README.md` 참조).

```bash
~/isaacsim/python.sh generation/dump_joint_names.py \
    --usd <H1 USD 경로> --robot-model unitree_h1
```
